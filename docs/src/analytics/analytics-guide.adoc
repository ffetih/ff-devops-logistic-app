[preface]
== About this guide

This guide is for developers of the analytics side: the loader that takes business events from Kafka into the analytics database, and that database itself.
The events and their topics belong to the logistics app; how they leave it is in the link:{url-logistics-guide}#kafka[Logistics App Guide]. How a problem on the cluster is traced is in the link:{url-operations-guide}[Operations Guide].

[[loader]]
== The analytics loader

A service of its own (`platform/ff-analytics/analytics-loader`, port 8086) that reads `ff.logistics.tms.shipment-delivered` and writes one row per delivered shipment into `ff_logistics_analytics`. It is that database's only writer and owns its schema. It shares the message format with the logistics app, not its code: it reads the JSON its own way (`ShipmentDeliveredMessage`), so either side can be built and released without the other.

[plantuml,analytics-loader,svg]
----
@startuml
queue "ff.logistics.tms.\nshipment-delivered" as topic
participant "ShipmentDelivered\nListener" as listener
participant "DeliveryStore" as store
database "ff_logistics_analytics" as db
queue "ff.logistics.tms.\nshipment-delivered.DLT" as dlt
topic -> listener : message (key = shipment id)
alt valid
  listener -> store : store
  store -> db : INSERT … ON CONFLICT (shipment_id) DO NOTHING
  listener -> topic : commit offset
else broken (not JSON, a field missing, a bad tenant id)
  listener -> dlt : the message as it came, with the reason in its headers
  listener -> topic : commit offset: the next message is read
else the database is down
  listener -> listener : wait 1 s, 2 s, 4 s … 30 s, and try again, without end
end
@enduml
----

[[failures]]
=== Two kinds of failure

A message that cannot be loaded either never will be, or cannot be loaded *yet*. The loader tells the two apart and treats them oppositely (`KafkaErrorHandling`):

[cols="1,2,2",options="header"]
|===
| Failure | Example | What happens

| Broken message (`InvalidMessageException`) | Not JSON; `tenantId` missing or not a tenant id; a negative distance | Retrying cannot help. It goes to `<topic>.DLT` at once, unchanged, with Spring's headers saying why (`kafka_dlt-exception-message`) and where it came from (`kafka_dlt-original-topic`, partition, offset). The next message is read.
| Anything else | PostgreSQL restarting or down | Retrying is the fix. The partition waits, 1 s doubling up to 30 s, without end, and continues where it stopped. Nothing is skipped and nothing is loaded out of turn.
|===

Sending a database outage to the dead-letter topic would empty the topic into it within seconds; waiting on a broken message would stop every message behind it for good. The dead-letter topic is created by the loader when it starts, with one partition; it is read by a person, not by a program.

[[at-least-once]]
=== Loaded once, read at least once

Kafka hands a message to the loader at least once: the offset is committed after the row is written, so a loader that stops in between reads the message again. The logistics app may also send a delivery twice. The shipment id is the table's primary key and the insert is `ON CONFLICT DO NOTHING`, so a second copy changes nothing. The metric `analytics.loader.deliveries` counts both, tagged `result=inserted` or `duplicate`; `analytics.loader.dead.letters` counts what went to a dead-letter topic.

=== The message it reads

[cols="2,1,4",options="header"]
|===
| Field | Required | Check

| `shipmentId` | yes | a UUID; the key of the row
| `tenantId` | yes | the platform's tenant id format (`TenantIds`), the same rule the tokens follow
| `shipmentNumber` | yes | at most 40 characters
| `customerOrderReference` | no | at most 64 characters
| `totalDistanceKm`, `savedCo2eKg` | yes | numbers, not negative
| `deliveredAt` | yes | an ISO-8601 instant
|===

Any other field is ignored, so the logistics app may add fields without the loader's release.

[[database]]
== The analytics database

`ff_logistics_analytics`, a second database on the cluster's PostgreSQL server. The server's image creates databases only on an empty volume, so the loader's chart brings a PreSync step that creates it if it is missing (`database.create`, `templates/job-database.yaml`), before Flyway migrates it in the next PreSync step:

[source,text]
----
sync analytics-loader
  PreSync  weight -1  analytics-loader-database-…  CREATE DATABASE ff_logistics_analytics, if missing
  PreSync  weight  0  analytics-loader-migrate-…   Flyway, the image's migrate profile
  Sync                Deployment analytics-loader   consumes
----

Its tables have no module prefix: the whole database is analytics.

[cols="2,4",options="header"]
|===
| Table | Rows

| `shipment_deliveries` | One per delivered shipment: tenant, number, order reference, distance, CO~2~e saved, `delivered_at`, and `loaded_at`, when the loader stored it
| `tenant_delivery_monthly` | One per tenant and month: delivered shipments, distance, CO~2~e saved, and `refreshed_at`, when it was last counted (<<rollup>>)
| `delivery_month_changes` | The months whose figures are out of date: the rollup's to-do list. Readers do not see it.
|===

Every table has the same row-level security (<<rls>>).

[[rls]]
== One tenant per reader: row-level security

The logistics app keeps tenants apart in its code: Hibernate adds `tenant_id = ?` to every query. The analytics database will be read by tools that know nothing of that code, dashboards first (S9). So the rule moves into the database: PostgreSQL itself filters every row, whatever the SQL.

[plantuml,analytics-rls,svg]
----
@startuml
skinparam componentStyle rectangle
[analytics loader\n(superuser: no policy applies)] as loader
[dashboard, report\n(analytics_reader)] as reader
database "shipment_deliveries" {
  [policy tenant_isolation:\ntenant_id = current_setting('app.tenant_id')\nOR current_setting('app.all_tenants') = 'on'] as policy
}
loader --> policy : writes every tenant's rows
reader --> policy : SET app.tenant_id = 'ff-eu-freight'\nthen any SELECT
@enduml
----

[cols="2,3",options="header"]
|===
| Session | Sees

| `analytics_reader`, nothing set | No row. A forgotten setting shows nothing rather than everything.
| `SET app.tenant_id = 'ff-eu-freight'` | That tenant's rows only, in every query, join and aggregate
| `SET app.all_tenants = 'on'` | Every tenant's rows: the platform's own reports, never a tenant's dashboard
| The loader (a superuser) | Everything; it writes every tenant's rows. A superuser or a `BYPASSRLS` role is above every policy.
|===

Four details make it hold:

* *`FORCE` as well as `ENABLE`.* `ENABLE ROW LEVEL SECURITY` exempts the table's owner. `FORCE` holds the owner to the policy too, so only a superuser or `BYPASSRLS` role is above it, never a role that merely created the table.
* *`current_setting(name, true)`* answers null for a setting the session never made, instead of an error, and `tenant_id = null` is never true: no row.
* *The scope changes only between statements.* `set_config()` would let one statement widen its own scope half way through: `SELECT set_config('app.all_tenants', 'on', false), count(*) FROM …` reads its later rows with the new value. A dashboard lets a viewer write such an expression into a chart. So no role but a superuser may call `set_config()` in this database (`REVOKE … FROM PUBLIC`); `SET` still works, and `SET` is a statement of its own.
* *The reader reads, and only what it is given.* `SELECT` on the analytics tables, nothing on `flyway_schema_history`, no `INSERT`; `WITH CHECK` would refuse a row of another tenant even if it could write.

The role is created by the loader's migration (`V2`), with the password of the `analytics-reader-credentials` Secret (`deploy/platform/postgres`) as a Flyway placeholder. Roles belong to the server, not to one database: it is created once and kept. `RowLevelSecurityTest` connects as the reader and tries each of the rows above.

To see it on the cluster:

[source,bash]
----
kubectl -n ff-logistics exec -it deploy/postgres -- psql -h localhost -U analytics_reader -d ff_logistics_analytics
# password: analyticsReader2026
select count(*) from shipment_deliveries;                    -- 0: no tenant named
set app.tenant_id = 'ff-eu-freight';
select count(*) from shipment_deliveries;                    -- that tenant's deliveries
select set_config('app.all_tenants', 'on', false);           -- ERROR: permission denied for function set_config
----

[[rollup]]
== Per tenant and month: the rollup

A dashboard asking "how many deliveries, how many kilometres, how much CO~2~e saved, per month" should not add up every delivery ever loaded each time it is opened. `tenant_delivery_monthly` holds the answer, one row per tenant and month, counted by the loader itself (`MonthlyDeliveryRollup`).

The trick is a to-do list. Think of a ledger with a sticky note on every page that changed: the bookkeeper re-adds only the pages with a note, and takes the note off as he does.

[plantuml,analytics-rollup,svg]
----
@startuml
skinparam componentStyle rectangle
[Kafka message] as msg
database "analytics database" {
  [shipment_deliveries] as d
  [delivery_month_changes\n(to-do list)] as todo
  [tenant_delivery_monthly] as m
}
[DeliveryStore] as store
[MonthlyDeliveryRollup\nat start, then every 5 min] as rollup
msg --> store
store --> d : insert (once per shipment)
store --> todo : mark its month,\nsame statement
rollup --> todo : take the marks
rollup --> d : recount those months
rollup --> m : upsert the figures
@enduml
----

* *The mark goes with the row.* One statement stores the delivery and marks its month (`with stored as (insert …) insert into delivery_month_changes …`). A delivery is never stored without its mark, and there is no clock to compare, so nothing slips between two runs. A delivery read twice is stored once and marks nothing.
* *A run takes the marks and recounts in one statement* (`with changed as (delete … returning …) insert … on conflict do update`). If the run fails, the delete is rolled back with it, and the marks wait for the next run. Two runs at once cannot both take the same mark.
* *A month is recounted, never added to.* The figures come from all of that month's rows each time, so a delivery for September read in November puts September right, and running twice changes nothing.
* *A month is a UTC calendar month* (`DeliveryMonth`, the one place that says so, used by both statements). A delivery at 01:30 on 1 November in Istanbul is 22:30 UTC on 31 October: October. Local months would need each tenant's time zone, which the platform does not record yet.

It runs once when the loader has started (so a new version's figures are there at once; `V3` marks every month that already had deliveries), then on `ANALYTICS_ROLLUP_CRON`, every five minutes. The cost follows what arrived since the last run, not the history. `rollUpAll()` rebuilds every month from every delivery: a repair, not the routine.

[cols="2,4",options="header"]
|===
| Metric | Meaning

| `analytics.rollup.pending` | Tenant-months marked and not recounted yet; drops to 0 at each run
| `analytics.rollup.last.success` | When the figures were last brought up to date (epoch seconds; 0 = never since the start)
| `analytics.rollup.months` | Tenant-months recounted, in total
| `analytics.rollup.duration` | Time per run
|===

`tenant_delivery_monthly` has the same row-level security as the deliveries (<<rls>>), and `analytics_reader` may read it. `MonthlyDeliveryRollupTest` covers tenants and months apart, the UTC month boundary, a late delivery, a repeated one, and the repair.

[[try-it]]
== Try it on the cluster

After a delivery in the logistics app's walkthrough, the loader has stored it within a second:

[source,bash]
----
kubectl -n ff-logistics exec deploy/postgres -- psql -U fflogistics -d ff_logistics_analytics -c \
  "select shipment_number, tenant_id, saved_co2e_kg, delivered_at, loaded_at from shipment_deliveries order by loaded_at desc limit 5"
----

The monthly figures, at most five minutes later (or at once after a restart of the loader):

[source,bash]
----
kubectl -n ff-logistics exec deploy/postgres -- psql -U fflogistics -d ff_logistics_analytics -c \
  "select tenant_id, delivery_month, delivered_shipments, total_distance_km, saved_co2e_kg, refreshed_at from tenant_delivery_monthly order by 2 desc, 1"
----

A broken message on purpose, then the dead-letter topic:

[source,bash]
----
echo 'broken-1:{"tenantId": "Not A Tenant"}' | kubectl -n ff-logistics exec -i kafka-0 -- /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic ff.logistics.tms.shipment-delivered --property parse.key=true --property key.separator=:
kubectl -n ff-logistics exec kafka-0 -- /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic ff.logistics.tms.shipment-delivered.DLT --from-beginning --timeout-ms 5000 \
  --property print.key=true --property print.headers=true
kubectl -n ff-logistics logs deploy/analytics-loader | grep 'sent to'
----

The consumer prints the message with its key and Spring's headers, among them `kafka_dlt-exception-message:tenantId is not a valid tenant id`; the loader's log has the same reason. The next delivery is loaded as before.
