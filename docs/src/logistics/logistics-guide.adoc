[preface]
== About this guide

`platform/ff-logistics/ff-logistics-app` is the logistics product: one deployable, built from modules that each own one part of the business.
This guide is for developers who change it: which modules exist, what each may use, and how its parts work.
How it is built, released and secured is in the link:{url-platform-guide}[Platform Guide]; how callers get a token is in the link:{url-identity-guide}[Identity Service Guide].

[[modules]]
== Modules

The app is a modular monolith. Spring Modulith treats every top-level package under `com.siose.ff.logistics` as a module, and `ModularityTest` holds them to three rules:

* *The base package is the module's API.* Other modules may use the public types in `com.siose.ff.logistics.<module>`; its sub-packages (`api`, `domain`, `service`) are internal.
* *Dependencies are declared.* `package-info.java` lists the modules it may use in `@ApplicationModule(allowedDependencies = ...)`. Anything else fails the build.
* *No cycles.* If two modules need each other, one of them publishes an event instead (S6).

A module that keeps these rules can later move into a service of its own without untangling it from the rest: its callers already use only its API.

[plantuml,logistics-modules,svg]
----
@startuml
skinparam componentStyle rectangle
package "logistics-app" {
  [caller] as caller
  [release] as release
  [standards] as standards
  [wms] as wms
  [tms] as tms
  [geo (S7)] as geo
  [reporting (S9)] as reporting
}
wms --> standards
tms --> standards
geo --> standards
reporting --> standards
reporting ..> tms : events
@enduml
----

[cols="1,2,3",options="header"]
|===
| Module | May use | Owns

| `caller` | nothing | `GET /api/v1/me`: the tenant, user and roles the app took from the token
| `release` | nothing | The `releaseSwitch` health contributor read by the canary analysis
| `standards` | nothing | GS1 check digits, ISO 6346 container codes, EN 16258 emissions (<<standards>>)
| `wms` | `standards` | Warehouses, bin locations, inbound ASNs (<<wms>>)
| `tms` | `standards` | Shipments with their legs, e-CMR number and CO~2~e footprint (<<tms>>)
|===

The base libraries (`siose-ff-base-*`) are not modules of the app; every module may use them.

=== Adding a module

. Create the package `com.siose.ff.logistics.<module>` with a `package-info.java`: a display name and the modules it may use.
. Put what other modules may call in the base package; everything else in sub-packages.
. Add a row to the table above, and the module to the diagram.

[[standards]]
== Standards

`com.siose.ff.logistics.standards` holds the public standards the other modules build on, as pure functions: static methods, no state, no beans, no database.
A rule that a GS1 or ISO document defines is written once, here, and tested against the examples in that document.

[cols="2,3,3",options="header"]
|===
| Class | Standard | Used for

| `Gs1Standards` | GS1 General Specifications: Modulo-10 check digit | Warehouse and site numbers (GLN-13), trade items (GTIN), pallet labels (SSCC-18)
| `Iso6346ContainerCode` | ISO 6346: owner code, category, serial, Modulo-11 check digit | Containers and trailers on a transport leg
| `EmissionsCalculator`, `TransportMode` | EN 16258 (now ISO 14083) and the GLEC Framework | CO~2~e of a shipment and the saving against road only
|===

=== GS1 check digit

Every GS1 key ends in the same check digit.
From the right, the digits are weighted 3, 1, 3, 1, ...; the check digit brings the weighted sum up to the next multiple of ten.
Starting from the right is what lets one rule serve keys of every length.

[source,text]
----
GLN  0 6 1 4 1 4 1 0 0 0 0 1 | ?
x    1 3 1 3 1 3 1 3 1 3 1 3      (weights from the right: 3, 1, 3, ...)
sum  0+18+1+12+1+12+1+0+0+0+0+3 = 48   ->  next multiple of 10 is 50   ->  check digit 2
     0614141000012
----

An SSCC is the extension digit, the GS1 company prefix, a serial reference and the check digit, 18 digits in all.
The longer the company prefix, the fewer digits remain for the serial: a 7-digit prefix leaves 9, so one prefix numbers a billion pallets per extension digit.
`generateSscc18` refuses a serial that does not fit rather than cutting it.

=== ISO 6346 container code

[source,text]
----
C S Q U   3 0 5 4 3 8   3
└─owner─┘ └─serial──┘   check digit
      └ category: U container, J detachable equipment, Z trailer or chassis
----

Each of the first ten characters gets a value (digits their own; letters from A = 10 upwards, skipping 11, 22 and 33, so L = 23 and V = 34), multiplied by 2 to the power of its position.
The check digit is the sum modulo 11, with a remainder of 10 written as 0.

=== Emissions

For every leg of a transport chain: distance x weight x the mode's factor, in grams of CO~2~e per tonne-km, added up.
`EmissionsCalculator.footprint` also returns what the same cargo would have emitted by road all the way, because that is the comparison a customer makes when it moves part of the route to rail or sea.

[cols="2,1",options="header"]
|===
| `TransportMode` | g CO~2~e per tonne-km

| `ROAD` | 62
| `RAIL` | 22
| `SEA_RORO` | 31
| `INLAND_WATERWAY` | 28
| `AIR` | 602
|===

The factors are typical well-to-wheel averages for a practice project, not certified figures: a real carrier uses its own measured values.
For 22 t from Istanbul by Ro-Ro to Trieste (1450 km), block train to Cologne (1050 km) and 80 km by truck, the chain emits 1606.22 kg against 3519.12 kg by road only, 54.36 % less.

[[wms]]
== Warehouse management (WMS)

The WMS module knows where goods can be and what is about to arrive.
Its tables start with `wms_`; every row carries the tenant, and Hibernate adds `tenant_id = ?` to every query, so the repositories never mention a tenant and one tenant's warehouse is, for another tenant, simply not there (`404`).

[plantuml,wms-model,svg]
----
@startuml
hide circle
hide methods
skinparam classAttributeIconSize 0
class Warehouse {
  {field} code (unique per tenant)
  name
  {field} gln : GLN-13 (unique per tenant)
  gs1CompanyPrefix
  countryCode, city, latitude, longitude
  palletCapacity
}
class BinLocation {
  {field} code, e.g. A02-R11-L04 (unique per warehouse)
  kind : RACK | FLOOR | STAGING
  palletCapacity
}
class Asn {
  {field} asnNumber (unique per tenant)
  supplierName
  expectedArrival
  status : EXPECTED | RECEIVING | RECEIVED
  version
}
class AsnLine {
  lineNumber
  gtin : GTIN-8/12/13/14
  skuCode
  expectedQuantity
  receivedQuantity
}
class Pallet {
  {field} sscc : SSCC-18 (unique everywhere)
  gtin, skuCode
  quantity
  grossWeightKg
}
Warehouse "1" *-- "*" BinLocation
Warehouse "1" <-- "*" Asn : delivered to
Asn "1" *-- "1..*" AsnLine
Asn "1" <-- "*" Pallet : received from
BinLocation "1" <-- "*" Pallet : stands in
@enduml
----

Warehouse:: A warehouse, cross-dock or hub. Its GLN is the number partners know it by. The GLN must start with the GS1 company prefix, because a GS1 member numbers its own locations from its own prefix; the same prefix will start every pallet label printed there.
Bin location:: One addressable place inside a warehouse. The code is what is printed on the label at the place and what a scanner reads.
ASN (advance shipping notice):: The supplier's message that goods are on their way: EDIFACT DESADV, GS1 despatch advice. One line per GTIN, numbered from 1. The ASN and its lines are one aggregate: lines are only created and changed through the ASN, which keeps the rules in one place.
Pallet:: Goods of one ASN line, built into a pallet at receiving, labelled with an SSCC and put away into a bin location. From then on the SSCC is the pallet's identity for everyone in the chain.

=== API

All endpoints need `WAREHOUSE_OPERATOR` or `TENANT_ADMIN` (<<roles>>). Errors are RFC 9457 problems; the `type` says which rule was broken.

[cols="2,4,3",options="header"]
|===
| Request | Does | Refused with

| `POST /api/v1/wms/warehouses` | Registers a warehouse; code and country are stored upper case | `400 domain-validation` (GLN check digit, prefix), `409 warehouse-code-taken`, `409 warehouse-gln-taken`
| `GET /api/v1/wms/warehouses`, `/{id}` | The tenant's warehouses, by code | `404` for another tenant's id
| `POST /api/v1/wms/warehouses/{id}/bins` | Adds a bin location | `409 bin-code-taken`
| `GET /api/v1/wms/warehouses/{id}/bins` | The warehouse's bin locations, by code |
| `POST /api/v1/wms/asns` | Records an ASN with its lines; status `EXPECTED` | `400 domain-validation` (GTIN check digit, a GTIN twice), `404` unknown warehouse, `409 asn-number-taken`
| `GET /api/v1/wms/asns`, `/{id}` | The receiving plan: by expected arrival, then number |
| `POST /api/v1/wms/asns/{id}/pallets` | Receives one pallet: books the quantity on the GTIN's line, labels it with a new SSCC, puts it into the bin (<<receiving>>) | `400 domain-validation` (GTIN not on the ASN, bin not in its warehouse), `409 over-receipt`, `409 asn-already-received`, `409 bin-full`
| `GET /api/v1/wms/asns/{id}/pallets` | The pallets received against an ASN, by SSCC |
| `GET /api/v1/wms/pallets/{sscc}` | What a scanner asks when it reads a pallet label | `404` for another tenant's pallet
|===

=== Try it on the cluster

`nexus.planner` works for `ff-eu-freight` and holds `WAREHOUSE_OPERATOR` (how to get a token: `deploy/README.md`, "Calling the logistics app with a token").

[source,bash]
----
TOKEN=$(curl -s -X POST localhost:8085/sessions -H 'Content-Type: application/json' \
  -d '{"username":"nexus.planner","password":"fflogistics2026"}' | python3 -c 'import json,sys; print(json.load(sys.stdin)["accessToken"])')
AUTH="Authorization: Bearer $TOKEN"

WH=$(curl -s localhost:8081/api/v1/wms/warehouses -H "$AUTH" -H 'Content-Type: application/json' -d '{
  "code": "IST-HUB-01", "name": "Istanbul Hadimkoy Hub", "gln": "8690001000103", "gs1CompanyPrefix": "8690001",
  "countryCode": "TR", "city": "Istanbul", "latitude": 41.1025, "longitude": 28.6512, "palletCapacity": 12000}' \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["id"])')

curl -s localhost:8081/api/v1/wms/warehouses/$WH/bins -H "$AUTH" -H 'Content-Type: application/json' \
  -d '{"code": "A01-R01-L01", "kind": "RACK", "palletCapacity": 2}'; echo

curl -s localhost:8081/api/v1/wms/asns -H "$AUTH" -H 'Content-Type: application/json' -d '{
  "asnNumber": "DESADV-4711", "warehouseId": "'$WH'", "supplierName": "Bosch Bursa", "expectedArrival": "2026-11-24",
  "lines": [{"gtin": "8690001000011", "skuCode": "BRAKE-PAD-1", "quantity": 10}]}'; echo
----

Receive the ASN in two pallets, 8 units and then the last 2. The answer carries the SSCC and the ASN's new status, `RECEIVING` and then `RECEIVED`:

[source,bash]
----
ASN=$(curl -s localhost:8081/api/v1/wms/asns -H "$AUTH" | python3 -c 'import json,sys; print(json.load(sys.stdin)[0]["id"])')
for qty in 8 2; do
  curl -s localhost:8081/api/v1/wms/asns/$ASN/pallets -H "$AUTH" -H 'Content-Type: application/json' \
    -d '{"gtin": "8690001000011", "quantity": '$qty', "grossWeightKg": 412.5, "binCode": "A01-R01-L01"}'; echo
done
----

A third pallet answers `409 asn-already-received`.
Signed in as `geodispatch.operator` (tenant `ff-tr-distribution`), `GET /api/v1/wms/warehouses` returns `[]`, and the same warehouse id answers `404`.

[[receiving]]
=== Receiving and SSCC labels

One request is one pallet, the way a receiving clerk works: scan the goods, count them onto a pallet, print the label, scan the bin.

[plantuml,wms-receiving,svg]
----
@startuml
start
:lock the ASN (SELECT ... FOR UPDATE);
:lock the bin location;
if (bin already full?) then (yes)
  :409 bin-full;
  stop
endif
if (ASN received / GTIN not on it / more than the line still expects?) then (yes)
  :409 or 400;
  stop
endif
:book the quantity on the line;\nASN -> RECEIVING, or RECEIVED when no line is open;
:next value of wms_sscc_serial_seq;
:SSCC = 0 + company prefix + serial + check digit;
:save the pallet;
:201 with the SSCC;
stop
@enduml
----

[source,text]
----
0 8690001 000100001 0
│ └──┬──┘ └───┬───┘ └ check digit (GS1 Modulo-10)
│    │        └ serial reference: wms_sscc_serial_seq, 9 digits after a 7-digit prefix
│    └ GS1 company prefix of the warehouse operator (the warehouse's gs1CompanyPrefix)
└ extension digit: always 0 here
----

Why the serial comes from a database sequence:: An SSCC must never be issued twice, and GS1 forbids reusing one within a year of shipping the pallet. A PostgreSQL sequence hands out each value once, across restarts and across every pod of the app; a counter in memory would repeat numbers after a restart, and "highest so far plus one" would hand the same number to two requests at the same moment.
A serial is not given back when the request fails afterwards, so the numbers can have gaps. A gap is allowed; a number used twice is not.

Why the ASN is locked:: Two scanners can receive against the same ASN at once. Without a lock, both would read "2 units still open", both would book 2, and the line would show 12 of 10. `findForReceivingById` takes a row lock until the transaction ends, so the second request waits, then sees 0 open and gets `409`. The bin is locked the same way, for its last free place, and always after the ASN, so two requests can never wait for each other.


[[tms]]
== Transport management (TMS)

The TMS module plans shipments: one piece of equipment, carrying goods labelled with an SSCC, from origin to destination over a chain of transport legs.
Its tables start with `tms_`, and like every table they are filtered by tenant.

[plantuml,tms-model,svg]
----
@startuml
hide circle
hide methods
skinparam classAttributeIconSize 0
class Shipment {
  {field} shipmentNumber : SHP-10001 (from tms_shipment_seq)
  {field} ecmrNumber : ECMR-10001
  consignorName, consigneeName
  {field} equipmentCode : ISO 6346
  {field} sscc : SSCC-18
  {field} incoterm : Incoterms 2020
  origin, destination
  grossWeightKg
  {field} footprint : distance, CO2e, road only, saved, %
  {field} status : see the lifecycle
  pickedUpAt, departedAt, deliveredAt
  receivedBy
  version
}
class TransportLeg {
  sequenceNo
  {field} mode : SEA_RORO | RAIL | ROAD | ...
  origin, destination
  distanceKm
  carrierReference
}
Shipment "1" *-- "1..*" TransportLeg : route, in order
@enduml
----

Shipment:: The consignment as the planner books it. The shipment and its legs are one aggregate; the legs are only created through the shipment.
e-CMR number:: The number of the electronic consignment note. The CMR convention's waybill travels with every international road transport in Europe; e-CMR is its electronic form. One per shipment here, numbered with the shipment.
Equipment:: The container or trailer, by its ISO 6346 code. A wrong check digit is refused, so a typo cannot book the wrong box.
Incoterm:: Who pays which part of the journey and where the risk passes, from the sales contract (Incoterms 2020: `EXW` … `DDP`).
Route:: The legs in order. The first starts at the shipment's origin, each next one where the previous ended, the last ends at the destination; a gap is refused with the leg that breaks the chain.
Footprint:: EN 16258 from `standards`, calculated when the shipment is planned and kept: a later change of emission factors does not rewrite what a customer was told.

[[shipment-lifecycle]]
=== Lifecycle

[plantuml,tms-lifecycle,svg]
----
@startuml
hide empty description
[*] --> PLANNED : POST /shipments
PLANNED --> PICKED_UP : POST …/pickup
PICKED_UP --> DEPARTED : POST …/departure
PLANNED --> DEPARTED : POST …/departure\n(pickup not reported)
DEPARTED --> DELIVERED : POST …/delivery\n{"receivedBy": …}
DELIVERED --> [*]
@enduml
----

A shipment only moves forward. A step may be left out, because not every carrier reports every scan, but never repeated or taken back: a pickup after the departure answers `409 shipment-status-conflict`. Each step records its time (`pickedUpAt`, `departedAt`); a step that was left out keeps no time.

The delivery records who signed for the goods at the consignee, the name under the e-CMR's "goods received", and is the end: nothing comes after it.

[[delivered-once]]
==== Delivered once, also at the same moment

Two drivers' apps can confirm the same delivery within milliseconds. The lifecycle alone would not stop that: both requests read `DEPARTED`, both see that `DELIVERED` comes next, both write. The shipment therefore carries a `version`, and Hibernate makes every update conditional on it:

[source,text]
----
request A                                     request B
read SHP-10001: DEPARTED, version 1           read SHP-10001: DEPARTED, version 1
UPDATE … SET status='DELIVERED', version=2
  WHERE id=… AND version=1      → 1 row
commit                                        UPDATE … SET status='DELIVERED', version=2
                                                WHERE id=… AND version=1   → 0 rows
200 DELIVERED                                 409 concurrent-update (nothing changed)
----

A confirmation that arrives after the first has committed reads `DELIVERED` and is refused by the lifecycle instead (`409 shipment-status-conflict`). Either way the shipment is delivered exactly once; with four confirmations sent in parallel against PostgreSQL, one answers `200` and three `409 concurrent-update`.

This is optimistic locking: nothing is locked while a request works, and a conflict is found at the write. The WMS uses the other kind for receiving (<<receiving>>): a row lock that makes the second scanner wait. A wait suits receiving, where the second pallet is still valid and only has to come after the first; a refusal suits delivery, where the second confirmation is a duplicate.

=== API

All endpoints need `LOGISTICS_PLANNER` or `TENANT_ADMIN` (<<roles>>).

[cols="2,4,3",options="header"]
|===
| Request | Does | Refused with

| `POST /api/v1/tms/shipments/{id}/pickup`, `/departure` | Moves the shipment one step on (<<shipment-lifecycle>>) | `409 shipment-status-conflict`
| `POST /api/v1/tms/shipments/{id}/delivery` | Delivers it, with `{"receivedBy": "…"}` (<<delivered-once>>) | `409 shipment-status-conflict`, `409 concurrent-update`
| `POST /api/v1/tms/shipments` | Plans a shipment; numbers it, calculates the footprint; status `PLANNED` | `400 domain-validation` (ISO 6346 or SSCC check digit, a broken route), `400 invalid-payload` (unknown incoterm or mode)
| `GET /api/v1/tms/shipments`, `/{id}` | The tenant's shipments, newest first | `404` for another tenant's id
|===

=== Try it on the cluster

With the token from the WMS walkthrough (`nexus.planner` is also a `LOGISTICS_PLANNER`):

[source,bash]
----
curl -s localhost:8081/api/v1/tms/shipments -H "$AUTH" -H 'Content-Type: application/json' -d '{
  "consignorName": "Bosch Bursa", "consigneeName": "Rhein Parts GmbH",
  "equipmentCode": "CSQU3054383", "sscc": "106141411234567897", "incoterm": "DAP",
  "origin": "Istanbul Pendik", "destination": "Cologne Eifeltor", "grossWeightKg": 22000,
  "legs": [
    {"mode": "SEA_RORO", "origin": "Istanbul Pendik", "destination": "Trieste", "distanceKm": 1450, "carrierReference": "DFDS-PT-2611"},
    {"mode": "RAIL", "origin": "Trieste", "destination": "Cologne Eifeltor Terminal", "distanceKm": 1050, "carrierReference": "TXL-41877"},
    {"mode": "ROAD", "origin": "Cologne Eifeltor Terminal", "destination": "Cologne Eifeltor", "distanceKm": 80, "carrierReference": "TR-34-FF-0417"}]}'; echo
----

The answer carries `SHP-10001`, `ECMR-10001` and a footprint of 1606.22 kg CO~2~e against 3519.12 kg by road only, 54.36 % less.

Then move it along, with its id from the answer:

[source,bash]
----
SHP=$(curl -s localhost:8081/api/v1/tms/shipments -H "$AUTH" | python3 -c 'import json,sys; print(json.load(sys.stdin)[0]["id"])')
curl -s -X POST localhost:8081/api/v1/tms/shipments/$SHP/pickup -H "$AUTH"; echo
curl -s -X POST localhost:8081/api/v1/tms/shipments/$SHP/departure -H "$AUTH"; echo
for driver in A B C D; do      # four confirmations at once: one 200, the others 409
  curl -s -o /dev/null -w "%{http_code} " localhost:8081/api/v1/tms/shipments/$SHP/delivery -H "$AUTH" \
    -H 'Content-Type: application/json' -d '{"receivedBy": "Driver '$driver'"}' &
done; wait; echo
----
