[preface]
== About this guide

How the parts of the {project-name} fit together, how a change travels from a commit to the local cluster, and what every service shares: the base libraries, the build platform, security and multi-tenancy.
Step-by-step commands for the cluster, Argo CD and each Application are in `deploy/README.md`; the sprint plan is in `docs/backlog.md`.

[[architecture]]
== Architecture

=== Overview

Everything runs in one k3d cluster in WSL. Argo CD, inside the cluster, applies what is committed under `deploy/`; nothing else is applied by hand.

[plantuml,architecture,svg,subs=attributes+]
----

node "k3d cluster ff-logistics" {
  package "argocd" {
    [Argo CD\n:{port-argocd}] as acd
  }
  package "argo-rollouts" {
    [Rollouts controller] as ro
  }
  package "ff-logistics" {
    [logistics-app\nRollout :{port-app}] as app
    [identity\nDeployment :{port-identity}] as id

| Argo CD {argocd-version} | platform | Applies `deploy/` from `main`; manages its own installation.
| Argo Rollouts {rollouts-version} | platform | Releases the logistics app as a canary with an analysis.
|===

=== Technology stack

* Java {java-version}, Spring Boot {spring-boot-version}, Spring Modulith {spring-modulith-version} (the logistics app's modules)
* Maven through the wrapper; no root `pom.xml`, every project builds on its own (<<build-platform>>)
* k3d (k3s) in WSL, Helm for the services, Kustomize for the platform pieces
* GitHub Actions and GitHub Container Registry
* Argo CD and Argo Rollouts

[[delivery]]
== Delivery path

[plantuml,delivery,svg]
----
@startuml
start
:pull request;
:CI: build and test (build-all),\nrender every chart and kustomization,\nbuild these docs;
:merge to main;
:CI: publish an image for each service\nthe push changed (its folder, base/, the wrapper);
:CI: commit the new tag into\ndeploy/apps/<service>/image-local.yaml [skip ci];
:Argo CD polls Git (every minute):\nApplication OutOfSync;
:operator syncs;
:PreSync hook: Flyway migrates;
:Rollout: 25 % → analysis → 50 % → 100 %;
:PostSync hook: smoke test through the Service;
stop
@enduml
----

* *Only Git changes the cluster.* No automated sync on the services: `main` is the only environment, so a merged change waits for an operator to sync it.
* *One image per changed service.* A change to values or docs builds nothing; only the changed values reach the cluster on the next sync.
* *The tag is the commit.* Images are `ghcr.io/ffetih/ff-devops-logistic-app/<service>:<commit sha>`. CI writes the tag into `image-local.yaml`, a file nobody edits by hand, so the bot's commit never collides with a person's.
* *Migrations before pods.* A PreSync hook Job runs the same image in the `migrate` profile. If it fails, the sync stops and the running version keeps serving. Migrations must work for the old and the new version at once: expand first, contract a release later.
* *A canary decides by itself.* The analysis reads `/actuator/health/release` on the canary pod three times; one `DOWN` aborts the release and scales the canary back. Users stay on the stable pods throughout.
* *Every sync ends with a smoke test.* Once the release has all traffic, a PostSync hook Job signs in through the identity service and calls the API through its Service. A failed check marks the sync Failed; the release stays, and the failure is the signal to look.

[[base-library]]
== How a service uses the base libraries

The base layer is small libraries. Each does one job, depends only on what that job needs, and switches itself on through Spring Boot auto-configuration. A service picks the libraries it needs; it never writes an annotation or a configuration class for them.

[plantuml,base-libraries,svg]
----
@startuml
skinparam componentStyle rectangle
[ff-base-tenant\nTenantContext\n(no dependencies)] as tenant
[ff-base-security\nJWT resource server,\ntenant filter] as sec
[ff-base-persistence\n@TenantId entities,\nDatabaseSequences] as per
[ff-base-web\nRFC 9457 problems] as web
[ff-base-storage\ndocuments in S3,\npresigned links] as sto
sec --> tenant
per --> tenant
web --> tenant
sto --> web : 409, 404, 503
@enduml
----

[cols="1,2,2",options="header"]
|===
| Library | Auto-configuration | Settings

| `siose-ff-base-tenant` | none (plain Java) | -
| `siose-ff-base-security` | `TenantSecurityAutoConfiguration`: stateless filter chain, `@PreAuthorize`, tenant filter | `ff.security.tenant-claim`, `ff.security.header-fallback.*`
| `siose-ff-base-persistence` | `TenantPersistenceAutoConfiguration`: Hibernate tenant resolver, `DatabaseSequences` | -
| `siose-ff-base-web` | `ProblemDetailAutoConfiguration`: problem responses | -
| `siose-ff-base-storage` | `ObjectStorageAutoConfiguration`: `ObjectStoragePort`, reference-only by default, S3 when configured and the AWS SDK is on the classpath (<<documents>>) | `ff.storage.*`
|===

* The logistics app uses `tenant` directly and `security` and `web` at `runtime` scope: its code never imports them, only their auto-configuration is used. `persistence` joins with the first entity.
* *Replace* any piece by declaring your own bean: every auto-configured bean is `@ConditionalOnMissingBean`.
* *No product names in base:* role names, sequence names or bucket contents live in the service and reach a library through configuration.
* *Dependency hygiene:* base libraries fail the build on any unused or used-but-undeclared compile dependency; services only get warnings.

[[documents]]
=== Documents: siose-ff-base-storage

A document (a proof-of-delivery signature, an e-CMR) is reserved first and uploaded later, by the client, straight to the object store. The bytes never pass through the service: it only signs a short-lived link.

[plantuml,document-links,svg]
----
@startuml
participant Client as c
participant "Service\n(DocumentLinks)" as s
participant "Object store\n(RustFS, S3)" as o
c -> s : POST …/upload-link
s -> o : HEAD key
o --> s : 404, not stored yet
s --> c : PUT url, 15 min,\nContent-Type, If-None-Match: *
c -> o : PUT bytes, with both headers
o --> c : 200
c -> s : GET …/download-link
s -> o : HEAD key
s --> c : GET url, 15 min
c -> o : GET
o --> c : the document
@enduml
----

[cols="1,3",options="header"]
|===
| Rule | How

| One bucket, a prefix per tenant | Key `<tenant>/<category>/<reference>/<file>`, each part reduced to safe characters, so no value can climb out of its prefix (`ObjectKeys`). The location `s3://<bucket>/<key>` holds no endpoint or credentials and can be stored with the record.
| Only the caller's tenant | A link is signed only for a location under the caller's tenant prefix; anything else is `403`, even if the record was loaded wrongly (`DocumentLinks`).
| Written once (`BR-DOC-01`) | No upload link while the store holds the document: `409 document-already-stored`. The link itself is signed with `If-None-Match: *`, so a link issued earlier cannot overwrite it either: the store answers `412`, and a client that drops the header breaks the signature (`403`).
| Nothing to download yet | `404` instead of a link to the store's own XML error.
| Store unavailable | No store configured, no answer, or an error: `503 object-store-unavailable`. One call takes at most `ff.storage.s3.timeout` (10 s), retries included.
| Two addresses | The service talks to the store inside the cluster (`http://rustfs-svc:9000`); a client cannot resolve that name, and the host is part of the signature. Links are therefore signed for `ff.storage.s3.public-endpoint` (`http://localhost:9000`).
|===

[cols="2,3",options="header"]
|===
| Setting | Meaning

| `ff.storage.provider` | `reference-only` (default: keys only, nothing stored, links `503`) or `s3`
| `ff.storage.bucket` | `ff-documents`; created when the first document needs it
| `ff.storage.s3.endpoint`, `public-endpoint` | Where the service reaches the store, and where links point
| `ff.storage.s3.access-key`, `secret-key` | Empty: the AWS default credential chain (environment, profile, pod role)
| `ff.storage.s3.timeout` | Longest call to the store, 10 s
|===

`RustFsWriteOnceTest` checks the write-once rule against the RustFS version the cluster runs, in a container; it needs Docker or Podman, as CI has, and is skipped without.

[[build-platform]]
== Build platform

The projects do not inherit from `spring-boot-starter-parent`. Instead `base` owns two small POMs:

[cols="1,2,2",options="header"]
|===
| POM | Holds | Change it when

| `ff-base-bom` | Versions only: internal libraries plus the Spring Boot and Spring Modulith BOMs. | Upgrading Spring Boot or Spring Modulith, adding a library
| `ff-base-parent` | Build rules: Java {java-version}, encoding, plugin versions and settings, enforcer rules. | Changing how projects are compiled, tested or packaged
|===

* All projects use the groupId `com.siose.ff`; the artifactId is the folder name with the prefix `siose-ff-`; Java packages follow it (`com.siose.ff.base.<library>`, `com.siose.ff.identity`, `com.siose.ff.logistics`).
* Services never write a version for a base library; the BOM supplies it.
* `build-all.sh` installs the BOM, the parent and the libraries into `~/.m2`, then builds every service with its tests. CI runs the same script.

[[security-model]]
== Security model

A request passes three gates. Each is enforced by the framework, not by hand-written checks in the business code.

[cols="1,2,1",options="header"]
|===
| Gate | Enforced by | Failure

| *Who are you?* | The resource server verifies the access token locally: signature (JWKS from the identity service), expiry, issuer `{keycloak-public}/realms/{keycloak-realm}` and audience `{keycloak-client}`. The token must carry a well-formed `tenant_id`. | 401
| *What may you do?* | Realm and client roles become `ROLE_*` authorities (`TenantJwtAuthenticationConverter`). Controllers declare `@PreAuthorize`. | 403
| *Whose data?* | `TenantContextFilter` puts the token's tenant into `TenantContext`. With the first entity, Hibernate `@TenantId` adds `tenant_id = ?` to every query. | not found
|===

Actuator's health and info stay open: the probes and the canary analysis use them.

=== Local profile

`application-local.yml` of the logistics app sets `ff.security.header-fallback.enabled: true`, for runs from the IDE:

* JWT validation is off. The caller is identified by `X-Tenant-Id`, `X-User-Name` and `X-User-Roles` (comma-separated).
* Without `X-User-Roles` the caller gets `REPORT_VIEWER`, the narrowest role.
* A request without `X-Tenant-Id` gets 401.

CAUTION: The chart never sets the `local` profile. Never enable it outside a developer machine: anyone could claim any tenant and role.

[[multi-tenancy]]
== Multi-tenancy

* A tenant id has one format, `TenantIds` in `siose-ff-base-tenant`: 2 to 64 lower-case letters, digits and hyphens, starting with a letter or digit. A token with any other `tenant_id` is refused with 401, so nothing downstream cleans or rewrites a tenant id.
* There is no default tenant. Code that runs without one cannot save data, and reads return nothing.
* From the first entity on, `TenantAwareEntity` is the base class of every entity; its `tenant_id` column is `@TenantId`, and Hibernate filters every query by the tenant in `TenantContext`.

Rules:

* A guide starts with `include::../_attributes.adoc[]`. Link to another guide with the attributes defined there, for example `+link:{url-identity-guide}#configuration[Identity Service Guide]+`; never with a file path.
* Values that appear in several places (ports, versions, the realm name) go into `_attributes.adoc` and are used as `\{port-app}`.
* A new guide goes under `docs/src/<name>/` as `<something>-guide.adoc`, with an output folder in `build-docs.sh`, a `url-…` attribute, a line in `index.adoc`, and the two revision includes.
* Update the guide in the same commit as the code change. `docs/build/` is generated; it is not committed.

=== Revision history

Every guide ends with a *Revision history* appendix, and its header shows the latest revision. Both come from git: `docs/revisions.sh` runs first in the build and writes, for each guide, the latest commit that touched it and the list of all of them (`git log --follow`, merges left out). The subject of a commit that changes a guide is what readers see, so it is written for them. CI checks out the full history for this.

[[faq]]
== Frequently asked questions

A change I merged is not in the cluster. Why?::
The services have no automated sync. Check that CI finished (for code changes: the "Publish image tags" commit), then `argocd app get <service> --refresh` and `argocd app sync <service>`.

A values change started no canary. Why?::
A change to values alone builds no image. The Rollout starts a new revision only when the pod template changes; an environment variable does, a Service setting does not.

Why are Keycloak, PostgreSQL and Argo Rollouts not in the ApplicationSet?::
Each is shaped differently (an upstream manifest, a volume that must never be pruned, a realm file), and there are few of them. The ApplicationSet covers what is alike: Spring services rendered by the shared chart.
